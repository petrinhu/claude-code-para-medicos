## 1. Restrição absoluta

**Zero código/YAML para o aluno LER.** Ele PEDE o pipeline ao Claude (prompt em linguagem clínica); o YAML (`.github/workflows/ci.yml`) fica nos bastidores. Aprendizagem por **comportamento observável**: push → na aba **Actions** do GitHub aparece a bolinha girando → vira ✓ verde ou ✗ vermelho. A saída do CI é lida como **laudo** (verde=normal, vermelho=alterado), sempre traduzida. Únicos blocos técnicos: prompts + comandos `git add/commit/push` + cliques na web.

## 2. Analogia central — o controle de qualidade que roda AUTOMÁTICO

Continuidade das aulas 33-34 (amostra-controle). A dobra nova: **o controle deixa de depender da memória humana.** No laboratório, o gatilho é o relógio ("toda manhã, sozinho, antes do 1º paciente"). No app, o gatilho é a **entrega (push)**: "você sobe uma mudança, e isso, sozinho, dispara o controle — você não aperta o botão, o ato de entregar aperta por você."

**Âncora:** *"Nas últimas aulas o controle existia, mas alguém tinha que apertar o botão — VOCÊ tinha que lembrar de rodar. Hoje o controle roda sozinho. Ninguém aperta nada."*

Apoio: a prescrição eletrônica que checa interação medicamentosa **antes** de você assinar — ninguém pediu a checagem, ela aconteceu no caminho.

## 4. As 2 perguntas conceituais (Seção 3)

**P1 — Por que um robô, se você já roda na sua máquina?** (a) roda mais rápido; (b) **porque você, humano, esquece — e o robô não; ele roda SEMPRE, a cada entrega, mesmo quando você está cansado e pula o controle**; (c) roda testes melhores. → **(b).** Critério: CI não é redundância, é a garantia de que o controle SEMPRE roda, independente da sua memória. É a rede de segurança contra o esquecimento.

**P2 — O robô ficou vermelho numa entrega. O que isso significa?** (a) nada, é só aviso, pode ignorar; (b) **que aquela entrega tem uma regra quebrada e não deveria ser usada/publicada até consertar — vermelho é um portão fechado**; (c) o robô está com defeito. → **(b).** Planta o conceito de "CI como porteiro" (gancho para a aula_36). Critério: vermelho = a entrega não está pronta; consertar vem antes de seguir.

## 5. Os prompts (input copiável — o aluno não lê YAML)

**Prompt 0 — blindar git + LGPD** (em linguagem natural): pedir ao Claude para conferir, sem mostrar saída crua: (1) que o projeto está conectado ao repo `clinmd-tribe` no GitHub (remote `origin`) e o último commit foi enviado; (2) que `data/` (banco, artigos, banco vetorial) está no `.gitignore` e nunca sobe. Se algo faltar, o Claude conserta e confirma em 1 frase. *Reforça LGPD de forma auditável ("o paciente não sobe").*

**Prompt 1 — criar o pipeline CI** (linguagem clínica): "toda vez que eu der push, um robô do GitHub deve instalar as dependências com `uv` e rodar os meus testes com `uv run pytest`, mostrando ✓ verde se passarem ou ✗ vermelho se falharem". Requisitos: roda os mesmos testes que rodo local; dispara no push da `main` e manualmente; **escopo do 1º pipeline = testes determinísticos (calculadora + checklist)** — ver §7; não acessa `data/`. "NÃO me mostre o YAML; me diga (1) que está pronto, (2) os comandos git para enviar, (3) onde no GitHub ver a bolinha."

## 6. Demonstração observável (3 momentos)

1. **Primeiro verde:** `git add/commit/push` → aba **Actions** → bolinha amarela girando → etapas viram ✓ → ✓ verde no topo. *"Eu não digitei pytest — o robô digitou por mim, no servidor, no instante do push."*
2. **Hábito:** uma mudança trivial + push → nova bolinha → verde (mostra que é automático a cada entrega).
3. **CLÍMAX — sabotagem (espelha as aulas 33-34):** Prompt sabota o AVC prévio (2→1), "não rode nada na minha máquina"; `push` → aba Actions → ✗ **vermelho no servidor**; clicar mostra o guardião do AVC com ✗. *"Eu não rodei nada aqui — o robô pegou sozinho, no instante do push, longe de qualquer paciente."* → Prompt conserta (AVC volta a 2) → push → ✓ verde.

## 7. LGPD + ganchos + escopo

**LGPD (3 pontos):** Prompt 0 audita `data/` no `.gitignore` (prático/auditável); narração de que sobe "a receita do app e os controles fictícios — nunca o paciente"; encerramento (síntese: código é seu, dado nunca saiu). Nota: não inflar — aqui não há PHI em jogo, o reforço é de *princípio* (a chave é sua, o dado não sai), estendido ao código.

**Gancho aula_36:** "hoje o robô AVISA — verde ou vermelho. Mas ele ainda te deixa entregar mesmo com vermelho, se você ignorar. E se o robô pudesse BLOQUEAR — virar um porteiro que não deixa código quebrado passar? Próxima aula." (Prepara branch protection.)

**Escopo do 1º pipeline:** só testes determinísticos (calculadora + checklist). Motivo: o modelo `sentence-transformers` do RAG baixa ~90MB no runner na 1ª execução → risco de lentidão/timeout ao vivo. O RAG entra no CI na aula_36. Divisão didática limpa.

## 8. Notas de produção

1. **GitHub Actions é habilitado por padrão** em repos — basta criar `.github/workflows/ci.yml` e dar push; não precisa "ligar" via Settings (diferente do que seria no Forgejo). Confirmar.
2. **Runner gratuito do GitHub** (ubuntu-latest) — confirmar que a conta tem minutos de Actions disponíveis (contas free têm cota; repo privado consome cota). Gravar com a conta-piloto do Dr. Petrus num `clinmd-tribe-demo` se necessário.
3. **Escopo determinístico** evita o timeout do modelo de 90MB; se quiser CI completo, aquecer/cachear o modelo (decisão da aula_36).
4. **Sabotagem reversível:** working tree limpo/commitado antes; a sabotagem é um commit real que vai ao remote (ok, é didático); o conserto restaura. Não encerrar com o app quebrado.
5. **Token nunca no repo:** o aluno autentica com o git já configurado da aula_09; nenhuma chave colada em arquivo → gancho para S12.01 ("nunca suba seu token").
6. **Nomes/saída reais:** ajustar as falas que citam contagem de testes / aparência da aba Actions ao que aparecer na pré-gravação.
7. **HTML:** pandoc + `--metadata title=`.
