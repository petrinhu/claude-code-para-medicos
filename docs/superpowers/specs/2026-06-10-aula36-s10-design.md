# Aula 36 (S10.02) — O Porteiro: o robô que BLOQUEIA — Design / Spec

> **Brainstorming** — `learning-designer` + `engineering-coach` (YOLO). **Reconciliação técnica:** o coach venceu no mérito — branch protection só dá bloqueio observável via **Pull Request**; o pedagogo o admitiu. Sigo PR via **web** (cliques), escopo mínimo.
> Plataforma **GitHub**. **Destino:** `aula_36/roteiro.md` + `.html`.

## 0. Restrição absoluta
Zero código/YAML/config para o aluno LER. Só prompts em linguagem natural + comandos `git` + **cliques na web do GitHub**. O bloqueio é lido num único elemento visual: o botão **"Merge pull request"** (cinza+travado no vermelho → verde+clicável no verde). Nenhum YAML.

## 1. Decisão de escopo (reconciliada)
A aula entrega **três movimentos**: (1) completar o robô com o **RAG** (cache do modelo + job separado — resolve o débito da aula_35); (2) **o porteiro** — branch protection exigindo o CI verde, via **Pull Request pela web** (clímax); (3) **badge** "tests passing" no README (brinde de 2min).
**PR via web, não terminal:** o aluno cria a branch e abre/mergeia o PR por **botões** (terreno confortável); o terminal só faz `add/commit/push` (já dominado). **Escopo cortado:** sem `git branch` no terminal, sem resolver conflito, sem code review humano, sem múltiplas branches. Uma branch, um PR, um ciclo vermelho→verde→merge.

## 2. Analogias (duas, complementares)
- **Conceito de bloquear** (continuidade da aula_35, que já usou prescrição eletrônica): **soft-stop vs hard-stop**. Aula_35 = alerta amarelo que pisca e você clica "ciente" e prescreve a interação assim mesmo. Aula_36 = o sistema **não deixa assinar** a interação fatal; o botão fica cinza. *"Ele não te avisa do erro — ele não te DEIXA cometer o erro."*
- **O Pull Request** especificamente: **a antecâmara do bloco cirúrgico**. Você não entra no CC direto do corredor; passa pela antecâmara, confere paramentação, e só então a 2ª porta abre. O PR é a antecâmara do código: a mudança espera, o robô confere, a porta para a `main` só abre no verde.

## 3. Estrutura das 6 seções (~55min)
| # | Seção | Tempo |
|---|---|---|
| 1 | ABERTURA — O ALERTA QUE VOCÊ PODE IGNORAR (gancho aula_35; soft-stop vs hard-stop) | 5min |
| 2 | O GUARDIÃO QUE FALTAVA — RAG no robô (cache + job separado; porteiro completo antes de trancar) | 9min |
| 3 | VOCÊ DECIDE (2 perguntas) | 9min |
| 4 | A ANTECÂMARA E A FECHADURA — criar branch + PR (web) + ligar branch protection (Settings, cliques) | 11min |
| 5 | CLÍMAX — A PORTA QUE NÃO ABRE (sabota AVC na branch → PR → "Merge" cinza/travado no vermelho → conserta → "Merge" verde → merge) | 12min |
| 6 | ENCERRAMENTO — síntese + LGPD + badge (brinde) + gancho S11/aula_37 | 9min |

**Âncora de entrada:** retoma o gancho da aula_35 ("o robô ficou vermelho mas eu CONSEGUI entregar o quebrado; ele avisou mas não me impediu").
**Ordem RAG-antes-do-clímax:** completa o robô (porteiro completo) e deixa o clímax do bloqueio por último. Jobs separados → no clímax, o job calculadora fica vermelho rápido (não espera o RAG); narrar "um guardião vermelho já basta para trancar".

## 4. As 2 perguntas conceituais (Seção 3)
**P1 — robô de ontem vs porteiro de hoje?** (a) mais rápido; (b) testes melhores; (c) **os testes são os mesmos — muda a CONSEQUÊNCIA: ontem o vermelho avisava mas deixava entregar; hoje tranca a porta**. → **C.** Critério: a diferença entre avisar e impedir não está na inteligência do controle, está na consequência que você liga em cima dele.
**P2 — a porta trancou no vermelho; como abrir?** (a) forçar/burlar a entrada na marra; (b) desligar a trava, entregar quebrado, religar; (c) **consertar a regra — a porta abre sozinha quando o robô fica verde; a única chave é o conserto**. → **C.** Critério: porteiro de verdade só abre corrigindo o que ele apontou; se há atalho para burlar, é sugestão, não porteiro.

## 5. Prompts (input copiável — aluno não lê config)
- **Prompt 0** — terreno limpo: confere git/push, `data/` no `.gitignore`, e que o robô da aula_35 segue ok. (LGPD auditável.)
- **Prompt 4 (Seção 2)** — RAG no robô: rodar também os testes da busca; **cachear** o modelo de embeddings (não rebaixar a cada push); colocar a busca num **job separado** dos testes rápidos; não tocar `data/`. "Não me mostre config; diga (1) pronto, (2) comandos git, (3) o que verei na aba Actions (dois trabalhadores)."
- **Prompt 1 (Seção 4)** — antecâmara + guia de cliques: explicar e conduzir, passo a passo na **web**, como (a) criar branch "teste-do-porteiro" pela página do GitHub; (b) o comando git exato para enviar à branch (entregue pronto); (c) ligar em Settings→Branches a proteção da `main` exigindo o check do CI verde antes do merge — **sem exigir aprovação humana** (trabalha sozinho). "Não altere por mim; sou eu que clico. Você é meu guia de cliques."
- **Prompt 2 (Seção 5)** — sabotar na branch: AVC prévio 2→1 (CHA2DS2-VASc, ASCII), não mexe nos testes, não roda local.
- **Prompt 3 (Seção 5)** — consertar na branch: AVC volta a 2; confirma; lembra os comandos.
- **Prompt 5 (Seção 6)** — badge: selo "tests passing" no topo do README; comandos git; sem mostrar o conteúdo.

## 6. Demonstração do bloqueio (clímax, observável)
Sabota → `git push` (para a branch) → web → faixa "Compare & pull request" → "Create pull request" → na tela do PR: check do robô **amarelo girando** + botão **"Merge pull request" CINZA** ("Required statuses must pass") → vira **✗ vermelho** ("Merging is blocked") → **o aluno não consegue clicar em merge** (mata o gancho da aula_35: ontem entrava, hoje não) → Prompt 3 conserta → `git push` (mesma branch; o PR se atualiza sozinho) → check **✓ verde** ("All checks passed") → **"Merge" fica verde/clicável** → "Confirm merge" → "successfully merged" → deletar a branch. Um único elemento (o botão Merge) conta a história.

## 7. LGPD + ganchos
**LGPD:** a trava protege a **qualidade** do código, não muda o que sobe; `data/` segue protegida (o porteiro vigia o que entra no código, nunca toca no dado do paciente). Ganho de qualidade com zero erosão da privacidade.
**Gancho principal → S11/aula_37 (UI médica):** "a fundação está à prova de bala — contas certas e guardadas, checklist imutável, busca honesta, porteiro trancando a porta. Mas tem uma coisa que o PACIENTE vê primeiro: a cara do app. As cores, as letras, os ícones. Na próxima, agora que a fundação é sólida, a gente cuida do que o paciente VÊ." ## 8. Notas de produção
1. **RAG no runner:** confirmar o robô completo (com RAG) verde antes de gravar; cache do modelo configurado; run de aquecimento p/ o cache existir.
2. **Branch protection (CRÍTICO):** confirmar caminho exato (Settings→Branches **ou** Settings→Rules→Rulesets) na conta-piloto; o status check só aparece na lista **depois** de o CI ter rodado ≥1 vez; nome do check idêntico ao job (senão "pendente eterno").
3. **NÃO** ligar "Include administrators"/"Do not allow bypassing" — senão o dono solo se tranca fora da própria main (sem rota de correção emergencial).
4. **PR atualiza sozinho:** o 2º push (conserto) vai para a MESMA branch; o PR existente reavalia — não abrir PR novo.
5. **1º push da branch nova:** upstream pode não estar setado; o Claude entrega o comando de push correto (ex.: `git push origin teste-do-porteiro`) conforme o estado real; o aluno não adivinha flag.
6. **Reversibilidade:** a sabotagem vive na branch descartável (deletada no fim); a `main` nunca recebe o quebrado — sem working tree sujo no fim.
7. **Cota de Actions:** 2 jobs + cache consomem mais minutos; usar `clinmd-tribe-demo` se apertar.
8. **HTML:** pandoc + `--metadata title=`.
